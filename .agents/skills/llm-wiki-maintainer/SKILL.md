# Мейнтейнер LLM Wiki Skills

Веди изменения и выпуски этого репозитория от проверяемого запроса до
подтверждённого результата. Различай готовность локального изменения, merge,
публикацию GitHub Release и работоспособность установленного обновления.

Это локальный навык мейнтейнера. Не добавляй его в `skills/wiki-*`, manifest,
шаблоны или устанавливаемый комплект. Сам навык не даёт разрешения на merge,
push, tag, публикацию релиза или изменение настроек GitHub: выполняй внешние
действия в рамках поручения пользователя. Подготовка PR не означает выпуск.

## Контекст репозитория

Прочитай [AGENTS.md](../../../AGENTS.md), проверь cwd, Git status, remote,
актуальные ветки и существующие правила GitHub. Сохраняй чужие tracked,
untracked и ignored файлы; в коммит включай только свой scope. Всю работу с
репозиторием, включая подготовку изменения и релиза, веди в отдельном Git
worktree. Не редактируй основной checkout. Перед созданием worktree проверь,
что его каталог игнорируется Git.

- `skills/wiki-{query,ingest,update,lint}/` — четыре устанавливаемых навыка.
- `skills/wiki-query/references/` — общий контракт, формат raw, обвязка
  SimpleEn-RU и неизменяемые upstream-материалы `utr-source/` с лицензией и
  manifest. Правь обвязку отдельно от upstream.
- `bin/wiki/` — механические проверки и updater; `scripts/install.py` —
  установка; `templates/wiki/` — нейтральный начальный корпус.
- Набор не задаёт PDLC, OpenSpec, профиль или публикацию в defaults. Существующая
  wiki не мигрируется автоматически. Успех CLI не подтверждает смысл или
  актуальность знаний.

## Изменения и PR

`main` содержит выпущенное состояние, `dev` принимает новые фичи. Рабочую
ветку `codex/<тема>` создавай в отдельном worktree от актуальной `origin/dev`;
MR новой фичи направляй в `dev`. Релиз продвигает проверенное состояние
`dev → main` через отдельный MR. Если `dev` отсутствует, проверь remote и
сообщи о препятствии: не направляй фичу в `main` вместо `dev` и не создавай
общую ветку без поручения. Не обходи protection, обязательные checks и review.

1. Найди связанный issue или опиши новый запрос с границами и проверяемым
   результатом. Не создавай дубль для доработки того же запроса. Milestone
   назначай, когда версия и её scope действительно определены; не придумывай
   номер релиза или дату.
2. Меняй только нужные ресурсы. Для любого MR, включая документацию,
   обслуживание и релиз, обязательно содержательное описание изменений в
   `CHANGELOG.md`. Для обычного изменения добавь запись под `Unreleased`;
   если файла ещё нет, создай его в этом MR. Назови несовместимость и действия
   по обновлению, если они есть. Не заполняй историю догадками.
3. Проверь изменение. В MR укажи назначение, связанный issue, проверки,
   ограничения и фактическую целевую ветку. После ревью повтори проверки на
   актуальном head MR.

При ревью прочитай описание MR, общие комментарии, reviews и все review threads,
включая устаревшие; API с пагинацией обрабатывай полностью. Для каждого
замечания проверь исправление или согласуй обоснованный отказ, ответь в
исходном обсуждении. Не считай `resolved` заменой исправлению. Перед merge
убедись, что нет открытых замечаний, обязательные approvals и checks относятся
к текущему head, MR направлен в нужную ветку и не содержит посторонних правок.
В diff MR относительно его целевой ветки должна быть содержательная запись
`CHANGELOG.md` об этом изменении. Проверяй текст и diff, а не только наличие
файла: ранее существующая запись, удаление или правка пробелов не подходят.
Для релизного MR перенос записей в раздел версии считается таким изменением.
После новых коммитов перепроверь эти условия. Если информация о threads или
checks недоступна, готовность к merge не подтверждена.

## Проверки

Из корня репозитория:

```bash
python3 -m unittest discover -s tests -t .
git diff --check
```

Для `raw-lint` нужен PyYAML из `bin/wiki/requirements.txt`. Новые untracked
файлы проверь отдельно на whitespace и конец файла; перед коммитом проверь
staged состав и `git diff --cached --check`. Новый или изменённый навык проверь
валидатором навыков, если он доступен, и практическими сценариями решений.
Валидатор подтверждает формат, а не качество поведения.

Installer и updater проверяй только во временном проекте. Для изменений
устанавливаемых ресурсов проверь состав установленного комплекта и работу CLI.
Для этого локального навыка проверь, что installer его не копирует. Не
устанавливай набор в собственный checkout и не записывай в пользовательские
wiki ради теста.

## Выпуск обновления

1. Определи scope версии по завершённым изменениям и открытым задачам;
   назначь версию SemVer `MAJOR.MINOR.PATCH` по характеру изменений.
   Открытая задача не считается выполненной из-за включения в milestone.
2. Перенеси подтверждённые записи `Unreleased` в датированный раздел версии.
   Проверь breaking changes и инструкции обновления. Подготовь релизное
   изменение в отдельном worktree и проведи такое же ревью. Релизный MR
   направляй из `dev` в `main`.
3. Когда пользователь поручил публикацию, проверь merge commit релизного MR
   в `main`, затем поставь на этот commit тег `vMAJOR.MINOR.PATCH` и создай
   GitHub Release с той же версией. Релизные сборки и теги принадлежат только
   `main`; не тегай commit из `dev` или рабочей ветки. Подтверди соответствие
   тега, release и changelog. Не объявляй релиз опубликованным по одному лишь
   merge или tag.
4. Во временном проекте проверь установку опубликованного комплекта и
   `bin/wiki/update --check` для нужного канала. Канал `main` читает head
   `main`; канал `release` требует опубликованного стабильного GitHub Release
   и не переключается на `main` при его отсутствии. Проверяй реальный
   удалённый источник, когда утверждаешь доступность выпуска пользователям.
   После подтверждения результата закрой завершённые issue или milestone,
   если это входит в порученный процесс.

Сообщай ссылки на фактически созданные issue, PR, tag и release, результаты
проверок и достигнутый этап. Если публикация или проверка установленного
обновления ещё не состоялась, назови это явно.
